HELIX — ЖУРНАЛ ИЗМЕНЕНИЙ
========================

0.9.1 — оконные приложения, действия кнопок и bridges
-----------------------------------------------------

Добавлено
~~~~~~~~~

- Declarative app UI для `helix app`:
  - `app title "Название"` — заголовок окна;
  - `app size 700 500` — размер окна (в допустимом диапазоне);
  - `app button 1 "Добавить"` — графическая кнопка с числовым ID;
  - `app input` — явно оставить поле для числового ввода рядом с кнопками.
- Нажатие app-кнопки передаёт её ID в следующий `sense`. Код Helix обрабатывает ID обычными
  `if/else/end`; кнопки работают в Win32 runner и Linux GTK app window.
- `examples/button_app.hlx` — приложение-счётчик с кнопками «Добавить» и «Сбросить».
- Отдельная команда `bridge` для пяти интеграций с системными инструментами:
  - `bridge html "page.html"` — открыть HTML системным приложением/браузером;
  - `bridge css "style.css"` — открыть CSS назначенным системным приложением;
  - `bridge js "script.js"` — выполнить JavaScript установленным Node.js;
  - `bridge c "program.c"` — скомпилировать установленным `cc`/GCC и запустить;
  - `bridge cpp "program.cpp"` — скомпилировать установленным `c++`/G++ и запустить.
- HTML может подключать CSS и JavaScript стандартными ссылками `<link>` и `<script>`;
  команда `bridge html` открывает страницу в системной ассоциации. CSS сам по себе не является
  исполняемой программой.
- Внешние команды запускаются без скачивания и shell-интерполяции. На Linux используются
  `xdg-open`, `node`, `cc`, `c++`; на Windows — системное открытие файлов, `node.exe`, `gcc.exe`
  и `g++.exe`. Компиляторный результат создаётся во временной папке и удаляется после запуска.
  Если нужный инструмент не установлен или не находится через PATH, Helix показывает сообщение.
- В условиях `if` и `while` поддерживаются standalone truthy/falsy выражения: `if true`,
  `if false`, `while running`. Ноль считается ложью, любое ненулевое число — истиной.
- Windows Setup 0.9.1 запрашивает стандартное подтверждение UAC и устанавливается в Program Files.
  Установщик не обходит UAC и не повышает права молча.

Исправлено
~~~~~~~~~~

- Linux GTK runner закрывает pipe-дескрипторы после завершения программы; повторный запуск больше
  не оставляет эти дескрипторы открытыми.
- Win32 runner показывает финальный фрагмент вывода, даже если программа завершила последнюю строку
  без LF.
- Win32 UTF-8 output parser ограничивает незавершённую строку 64 KiB и сообщает о пропущенном
  фрагменте, вместо записи за границы статического буфера.
- Regression suite расширен проверками truthy/falsy условий, всех пяти bridge-команд и реальных
  GTK app-кнопок, включая передачу event ID в `sense`.

Проверено в этой сборочной среде
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- `make test` — языковые regression tests и end-to-end bridges (HTML/CSS/JS через test doubles,
  C/C++ через имеющиеся компиляторы): успешно.
- `make gui-test` — GTK/Xvfb tests: Enter для `sense`, app title/size, клик native-кнопки и
  создание marker-файла кодом Helix: успешно.
- Linux NASM engine собран и запущен; Windows x64 engine и GUI cross-compiled/linked.
- Windows GUI не запускался на реальном Windows компьютере в этой среде. AppImage/Setup для
  CachyOS и Debian также требуют практической проверки на целевых компьютерах.

Ограничения
~~~~~~~~~~~

- Интеграции не поставляют браузер, Node.js, GCC или G++; соответствующий инструмент должен быть
  установлен пользователем. HTML/CSS открываются системной ассоциацией, а JS выполняется Node.js,
  не браузерной console API.
- `bridge c` и `bridge cpp` синхронно компилируют и запускают source file. Это не IDE, не отладчик
  и не безопасная песочница: запускай только доверенный код.
- `app button` передаёт целочисленный ID через `sense`; произвольные типы событий, canvas,
  пользовательские функции, виджеты таблиц и layouts пока не реализованы.
- Helix остаётся ранней экспериментальной версией, а не заменой зрелым языкам и IDE.


0.9.2 — модули Helix, системные диалоги и отдельная app-оболочка
----------------------------------------------------------------

Добавлено
~~~~~~~~~

- `bridge helix "index.hlx"` запускает другой исходный `.hlx` тем же NASM runtime как дочерний процесс. Рабочая папка для GUI-runner устанавливается в каталог `main.hlx`, поэтому относительные пути модулей работают из проекта; вложенный скрипт должен иметь собственный корректный заголовок Helix.
- Native Dialog API:
  - `dialog "Заголовок" "Сообщение"` — информационное окно с кнопкой OK;
  - `cell result := 0` и `dialog result "Заголовок" "Вопрос"` — окно Yes/No, записывает 1 для Yes и 0 для No;
  - `{cell}` placeholders раскрываются в заголовке и сообщении.
- Windows app использует `MessageBoxW` с преобразованием UTF-8 в UTF-16; Linux GTK app использует `GtkMessageDialog`. Диалог синхронен: программа ждёт ответа.
- Linux `helix app` теперь имеет отдельную оболочку без output-pane терминала. Вывод `pulse` остаётся внутренним потоком runtime и не показывается как консоль в app window; UI-команды app и поле `sense` располагаются в самостоятельной поверхности.
- Win32 app mode скрывает терминальную output-панель; остаются native controls приложения.
- Regression tests расширены проверками модульного запуска, dialog fallback, чистого app-shell, кнопок и ввода.

Исправлено / ограничения
~~~~~~~~~~~~~~~~~~~~~~~~

- Linux runner передаёт запросы диалога через отдельный framed protocol, чтобы произвольные UTF-8 символы/табы в тексте не повреждали сообщение.
- В standalone console режиме без app-host `dialog` выводит понятное сообщение, не блокируется и записывает 0 в указанную ячейку.
- `bridge helix` и `dialog` не скачивают внешние компоненты.
- Windows source и NASM engine проходят сборку; end-to-end Windows GUI automation в этой среде не выполнялась.


Проверки и выпуск
~~~~~~~~~~~~~~~~~

- Пройдены Linux core regression и external bridge tests, а также Xvfb/xdotool проверки app window, Enter-ввода, native-кнопок и native Yes/No dialog с проверкой result-cell ветви.
- NASM x86-64 Linux engine и Win64 engine собраны; Win32 GUI/app smoke не запускался в реальной Windows-сессии.
- Native-dialog end-to-end проверен на Linux в Xvfb; Win32 engine собран, но реальный Windows MessageBox interaction test в этой среде не запускался.
